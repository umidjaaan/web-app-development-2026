# ЛР3 — контрольные вопросы

## Веб-сервис

Программа, которая по сети по стандартному протоколу (обычно HTTP) отдаёт данные и выполняет
операции в машиночитаемом виде — JSON или XML, а не HTML-страницы для человека. Клиентом может
быть любое приложение: SPA в браузере, мобильное приложение, другой сервер. Наш бэкенд — веб-сервис:
SPA из следующих лабораторных будет получать от него данные по адресам `/api/...`.

Основные подходы: **REST** (ресурсы + методы HTTP, обычно JSON), **RPC** (вызов удалённых процедур:
JSON-RPC, gRPC), **SOAP** (протокол обмена XML-сообщениями с описанием сервиса в WSDL).

## REST

Архитектурный стиль API (Рой Филдинг, 2000). Всё — **ресурсы** с адресами
(`/api/import_categories/5`), действие задаётся **методом HTTP**, результат — **кодом ответа**.
Ограничения REST:

1. **Клиент–сервер** — интерфейс отделён от хранения данных.
2. **Без состояния (stateless)** — каждый запрос содержит всё нужное, сервер не хранит контекст клиента между запросами.
3. **Кеширование** — ответ помечается как кешируемый или нет.
4. **Единообразный интерфейс** — ресурсы адресуются URI, работа с ними через стандартные методы, представления (JSON).
5. **Многоуровневость** — между клиентом и сервером могут быть прокси, балансировщики.
6. **Код по требованию** (необязательно) — сервер может передать клиенту исполняемый код.

У нас: `GET /api/import_categories` — список, `POST` — создание, `PUT …/:id/publish` — изменение
статуса, `DELETE …/:id` — удаление.

## RPC

Remote Procedure Call — вызов функции на другом компьютере так, будто она локальная: в запросе
передаются имя процедуры и аргументы, в ответе — результат. Примеры: JSON-RPC
(`{"method": "publishCategory", "params": [5]}`), gRPC (Protobuf поверх HTTP/2), XML-RPC.
Отличие от REST: в центре RPC — **действие** (глагол), в REST — **ресурс** (существительное)
и стандартный набор методов над ним.

## Методы HTTP

| Метод | Назначение | Тело | Безопасный | Идемпотентный |
|---|---|---|---|---|
| GET | получить ресурс | нет | да | да |
| HEAD | только заголовки ответа GET | нет | да | да |
| POST | создать ресурс / выполнить действие | да | нет | нет |
| PUT | заменить или изменить ресурс | да | нет | да |
| PATCH | частично изменить ресурс | да | нет | нет |
| DELETE | удалить ресурс | обычно нет | нет | да |
| OPTIONS | какие методы доступны (CORS) | нет | да | да |

Безопасный — не меняет данные на сервере; идемпотентный — повтор запроса даёт то же состояние.

## Заголовки HTTP

Метаданные запроса и ответа в виде `Имя: значение`:

* `Host` — имя сервера (обязателен в HTTP/1.1);
* `Content-Type` — формат тела (`application/json`, `multipart/form-data` — у нас при загрузке файлов);
* `Content-Length` — размер тела;
* `Accept` — какие форматы ответа понимает клиент;
* `Authorization`, `Cookie` / `Set-Cookie` — авторизация и сессии (ЛР4);
* `Cache-Control`, `ETag` — кеширование;
* `Location` — адрес при перенаправлении (3xx) или созданного ресурса;
* `User-Agent` — клиент; `Access-Control-Allow-Origin` — CORS.

Коды ответа: 1xx — информационные, 2xx — успех (200 OK, 201 Created, 204 No Content),
3xx — перенаправление (301, 302, 304), 4xx — ошибка клиента (400, 401, 403, 404, 409),
5xx — ошибка сервера (500, 502, 503).

## Версии HTTP

* **HTTP/0.9** (1991) — только `GET`, только HTML, без заголовков.
* **HTTP/1.0** (1996) — заголовки, коды ответа, методы `POST` и `HEAD`; новое TCP-соединение на каждый запрос.
* **HTTP/1.1** (1997) — постоянные соединения (keep-alive), обязательный `Host`, chunked-передача,
  кеширование, методы `PUT`, `DELETE`, `OPTIONS`. Запросы в соединении идут по очереди.
* **HTTP/2** (2015) — бинарный протокол, мультиплексирование (много запросов параллельно
  в одном TCP-соединении), сжатие заголовков HPACK, приоритеты, server push.
* **HTTP/3** (2022) — поверх QUIC (UDP): быстрее установка соединения, потеря одного пакета
  не задерживает остальные потоки, шифрование TLS 1.3 встроено.

## HTTPS

HTTP поверх TLS (раньше SSL), порт 443. Даёт **шифрование** (трафик не прочитать),
**целостность** (не подменить) и **аутентификацию сервера** (сертификат, подписанный центром
сертификации). При установке соединения (TLS handshake) клиент проверяет сертификат сервера,
стороны с помощью асимметричной криптографии (RSA / ECDHE) договариваются об общем ключе,
дальше данные шифруются быстрым симметричным шифром (AES, ChaCha20).

## Модель OSI ISO

Эталонная модель сетевого взаимодействия из 7 уровней (снизу вверх):

| № | Уровень | Что делает | Примеры |
|---|---|---|---|
| 7 | прикладной | данные приложений | HTTP, DNS, SMTP, FTP |
| 6 | представления | кодирование, сжатие, шифрование | TLS, JSON, UTF-8 |
| 5 | сеансовый | установка и поддержание сеансов | RPC, сессии TLS |
| 4 | транспортный | доставка между процессами, порты | TCP, UDP |
| 3 | сетевой | адресация и маршрутизация | IP, ICMP |
| 2 | канальный | передача кадров в одной сети, MAC-адреса | Ethernet, Wi-Fi |
| 1 | физический | сигналы и среда передачи | кабель, радио |

На практике используется стек TCP/IP из 4 уровней: прикладной (OSI 5–7), транспортный (4),
сетевой (3), канальный (1–2). Наш веб-сервис работает на прикладном уровне (HTTP) поверх TCP/IP.

# ЛР4 — контрольные вопросы

## Аутентификация и авторизация

* **Идентификация** — определить, кто это: найти пользователя по логину `umid`.
* **Аутентификация** — проверить, что это действительно он: сравнить введённый пароль
  с хешем bcrypt из таблицы `users`. В «Амфоре» — метод `POST /api/users/login`.
* **Авторизация** — решить, что ему можно: гостю — только список и лента, создателю —
  ещё черновик, добавление, публикация, удаление и лайк. В «Амфоре» — middleware
  `WithAuthCheck`: без токена методы создателя отвечают **401**.

Коды: **401 Unauthorized** — не аутентифицирован (нет токена, токен поддельный, истёк
или отозван); **403 Forbidden** — аутентифицирован, но прав не хватает.

## Куки (cookie)

Небольшие пары «имя=значение», которые сервер ставит заголовком ответа `Set-Cookie`,
а браузер **сам** присылает обратно в каждом запросе к этому сайту заголовком `Cookie`.
Атрибуты: `Expires`/`Max-Age` — срок жизни; `Domain`, `Path` — для каких адресов;
`HttpOnly` — недоступна из JavaScript (защита от XSS); `Secure` — только по HTTPS;
`SameSite=Strict|Lax|None` — отправлять ли с запросами с других сайтов (защита от CSRF).
Обычно в куке хранят идентификатор сессии.

## Сессия

Состояние пользователя на сервере между запросами. После входа сервер создаёт запись
«ид сессии → пользователь» (в памяти, БД или Redis) и отдаёт ид в куке. В следующих
запросах по ид из куки находит пользователя. Выход — удалить запись. Плюсы: сессию
можно отозвать мгновенно, в куке нет данных. Минус: сервер хранит состояние и на
каждый запрос обращается к хранилищу сессий.

## Redis

Резидентная NoSQL-база «ключ–значение»: данные хранятся в оперативной памяти, поэтому
операции занимают доли миллисекунды; на диск сохраняются снимки (RDB) или журнал (AOF).
Значения: строки, списки, множества, хеши, отсортированные множества. У ключа можно
задать время жизни (TTL) — по его истечении ключ удаляется сам. Применение: кеш,
сессии, чёрные списки токенов, очереди, счётчики.

В «Амфоре» Redis хранит **чёрный список JWT**: при выходе выполняется
`SET amphora.jwt.<токен> <логин> EX <секунд до конца срока токена>`. Middleware перед
выполнением метода проверяет `GET amphora.jwt.<токен>`: если ключ есть — 401.
Посмотреть: `docker exec -it rip-redis redis-cli -a rip`, затем `KEYS *`, `GET <ключ>`, `TTL <ключ>`.

## JWT (JSON Web Token)

Токен из трёх частей в Base64URL через точку: `header.payload.signature`.

* **header** — алгоритм и тип: `{"alg": "HS256", "typ": "JWT"}`;
* **payload** (claims) — данные: у нас `user_id`, `login`, `is_moderator`, `iat`
  (время выпуска), `exp` (срок действия), `iss` (издатель);
* **signature** — подпись `HMAC-SHA256(header + "." + payload, секрет)`.

Payload не шифруется — его может прочитать любой (jwt.io), поэтому пароли туда не
кладут. Подделать его нельзя: без секрета сервера подпись не сойдётся. Сервер ничего
не хранит — всё нужное в самом токене (stateless). Минус: выданный токен нельзя
«отменить», пока он не истёк, поэтому для выхода нужен **blacklist** (у нас в Redis).
Токен передаётся заголовком `Authorization: Bearer <токен>`. Для продления сессии
используют пару access-токен (короткий) и refresh-токен (длинный).

## SSO (Single Sign-On)

Единый вход: пользователь аутентифицируется один раз у **провайдера идентификации**
(IdP: Яндекс ID, Госуслуги, Keycloak, Google) и получает доступ ко многим приложениям
без повторного ввода пароля. Схема (OAuth 2.0 / OpenID Connect): приложение
перенаправляет на IdP → пользователь входит там → IdP возвращает в приложение код →
приложение обменивает код на токены (access, id_token) → по токену узнаёт пользователя.
Также SAML (XML-утверждения) в корпоративных системах. Плюсы: один пароль, единое
управление доступом; минус: IdP — единая точка отказа.

## Двухфакторная аутентификация (2FA)

Проверка двумя факторами из разных категорий: **знание** (пароль), **владение**
(телефон, ключ), **свойство** (отпечаток, лицо). Примеры второго фактора: код из SMS,
одноразовый код TOTP из приложения-аутентификатора (вычисляется из общего секрета и
текущего времени, меняется каждые 30 секунд), push-подтверждение, аппаратный ключ
FIDO2/U2F. Утечки одного пароля недостаточно для входа.

## RSA

Асимметричный алгоритм шифрования и подписи: пара ключей — **открытый** (публикуется)
и **закрытый** (секрет). Ключи строятся из двух больших простых чисел p и q:
n = p·q, открытая экспонента e, закрытая d с условием e·d ≡ 1 (mod φ(n)),
φ(n) = (p−1)(q−1). Шифрование: c = mᵉ mod n (открытым ключом), расшифровка:
m = cᵈ mod n (закрытым). Подпись — наоборот: подписывают закрытым ключом, проверяют
открытым. Стойкость основана на сложности разложения n на множители.

В JWT RSA используется в алгоритме **RS256**: токен подписывает сервер авторизации
закрытым ключом, а любой сервис проверяет открытым — секрет раздавать не нужно.
В «Амфоре» один сервис, поэтому используется симметричный **HS256** (один общий секрет).
RSA также применяется в HTTPS (обмен ключами и сертификаты) и SSH.
